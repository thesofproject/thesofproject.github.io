Audio Processing Components & Modules API#

In Sound Open Firmware (SOF), all audio processing components—including volume controllers, mixers, equalizers (EQ FIR/IIR), dynamic range compressors (DRC), sample rate converters (SRC/ASRC), crossover filters, and smart amplifiers—are architected as processing modules.

Modules can be built statically into the base firmware binary or compiled and loaded dynamically at runtime as relocatable ELF extensions using the Zephyr Loadable Extension (LLEXT) framework.

Architecture & Module Adapter Layer#

The pipeline execution graph decouples pipeline orchestration from signal processing algorithms through the Module Adapter layer:

+-------------------------------------------------------------------------+
|                             Pipeline Graph                              |
|              pipeline_create() / pipeline_connect() / walk_op           |
+------------------------------------+------------------------------------+
                                     | comp_ops (params, prepare, copy)
                                     v
+-------------------------------------------------------------------------+
|                        Module Adapter Component                         |
|                      DECLARE_MODULE_ADAPTER(name)                       |
|  - Adapts comp_ops into struct module_interface calls                   |
|  - Binds comp_buffer streaming queues to sof_source and sof_sink APIs   |
|  - Handles parameter fragmentation (large configuration blobs)          |
+------------------------------------+------------------------------------+
                                     | module_interface
                                     v
+-------------------------------------------------------------------------+
|                    Audio Processing Algorithm Module                    |
|     (Volume, Mixer, EQ FIR/IIR, DRC, SRC, ASRC, Smart Amp, etc.)       |
|  - init() / prepare() / process() / apply_config() / free()            |
|  - Pulls audio from struct sof_source                                   |
|  - Pushes audio to struct sof_sink                                      |
+------------------------------------+------------------------------------+
                                     | System Services
                                     v
+-------------------------------------------------------------------------+
|                      Host & RTOS System Services                        |
|          (Dynamic Heap Memory, Timers, Tracing, UUID, Math)             |
+-------------------------------------------------------------------------+

Module Lifecycle & Interface Contracts#

All audio modules implement struct module_interface:

  1. Initialization (`init`): Invoked when the module adapter component is instantiated (.new()). Allocates private algorithm state memory and registers default parameters. Typically marked __cold.

  2. Stream Preparation (`prepare`): Called when stream parameters are configured (.prepare()). Validates sample rates, channel counts, and buffer formats across all attached sources and sinks.

  3. Audio Block Processing (`process`): The primary execution callback running in the real-time processing loop. Consumes audio samples from source endpoint buffers and emits processed audio samples into sink endpoint buffers.

  4. Dynamic Configuration (`set_configuration` / `get_configuration`): Transfers runtime parameter blobs (filter coefficients, DRC curves, tuning parameters) from the host via IPC. Supports multi-fragment chunking for large configuration structures.

  5. Reset & Teardown (`reset`, `free`): Restores algorithm states to initial default settings and frees runtime buffers.

Streaming Endpoints: Source & Sink APIs#

Modules consume audio data exclusively via struct sof_source and produce audio data via struct sof_sink:

  • Source API (`source_get_data()`, `source_release_data()`): Allows the module to request a contiguous block of audio samples from the input stream. The underlying source handles circular buffer rollover, cache invalidation, and pointer advance.

  • Sink API (`sink_get_buffer()`, `sink_commit_buffer()`): Provides a destination memory region for the module to store processed samples. The sink commits the written bytes, flushes cache lines, and advances write pointers.

Dynamic LLEXT Loading & Identification#

Dynamic processing modules declare their ABI version, format compatibility tag, and unique UUID using standard SOF registration macros:

  • SOF_DEFINE_UUID(): Associates a 128-bit RFC 4122 UUID with the module driver.

  • struct sof_module_api_build_info: Encodes module build timestamp, git hash, and API version.

  • SOF_LLEXT_EXPORT_SYMBOL(): Exposes module entry points for dynamic symbol resolution.

int source_set_alignment_constants(struct sof_source *source, const uint32_t byte_align, const uint32_t frame_align_req)#

Set byte and frame alignment constants for source stream.

Sets frame_align_shift and frame_align of stream according to byte_align and frame_align_req requirements. Once the channel number and frame size are determined, the frame_align and frame_align_shift are determined too. These features are used by audio_stream_get_avail_frames_aligned() to calculate available frames.

Note

This must be called in component prepare or param functions only once after channel count and frame size are known and before stream copying begins. If omitted or called late, aligned availability can evaluate to zero and no data will be copied.

Parameters:

  • source – [inout] Pointer to source structure.

  • byte_align – [in] Processing byte alignment requirement.

  • frame_align_req – [in] Processing frames alignment requirement.

Returns:

0 on success, negative error code on failure.

uint16_t align_frame_cnt#

align_frame_cnt indicates minimum number of frames that satisfies both byte align and frame align requirements.

E.g: Consider an algorithm that processes in blocks of 3 frames configured to process 16-bit stereo using xtensa HiFi3 SIMD. Therefore with 16-bit stereo we have a frame size of 4 bytes, and SIMD intrinsic requirement of 8 bytes(2 frames) for HiFi3 and an algorithim requirement of 3 frames. Hence the common processing block size has to align with frame(1), intrinsic(2) and algorithm (3) giving us an optimum processing block size of 6 frames.

the free/available bytes of sink/source right shift align_shift_idx, the result multiplied by align_frame_cnt is the frame count free/available that can meet the align requirement.

struct sof_uuid#
#include <src/include/sof/lib/uuid.h>

UUID (Universally Unique IDentifier) structure.

Use DECLARE_SOF_UUID() to assigned UUID to the fw part (component implementation, dai implementation, …).

Use SOF_UUID() to store an address of declared UUID.

See existing implementation of components and dais for examples how to UUIDs are declared and assigned to the drivers to provide identification of the source for their log entries.

UUID for a new component may be generated with uuidgen Linux tool, part of the util-linux package.

FIXME: this struct scheme has an endianness bug. On BE systems, the same initialier for the a/b/c fields will produce different memory layout than on LE systems. Within C code, that’s fine, but when compared with external representations (c.f. topology) that pass UUIDs as a linear array of bytes, only one endianness will work. If SOF ever ships on a BE system all use of sof_uuid will need to be modified to byte swap the a/b/c values.

Some identifiers are taken from the module manifest. Since the module manifest structure (sof_man_module) is marked as packed, the pointer to the sof_uuid structure may not be properly aligned. To avoid possible problems with accessing fields of this structure from unaligned addresses, it has been marked as packed.
