Telemetry, Logging & Probes API#

Sound Open Firmware (SOF) incorporates a multi-tiered diagnostic, tracing, and telemetry architecture. The subsystem provides comprehensive visibility into real-time firmware execution, pipeline audio quality, hardware performance metrics, and system health with minimal latency and zero audio glitching.

Architecture & Subsystem Overview#

Diagnostic data in SOF is partitioned across four primary functional domains:

  1. Host DMA Tracing & Dictionary Logging: High-throughput binary logging via dedicated host DMA streams, early bootloader checkpoint trace codes (TRACE_BOOT_*), and panic crash dumps. Log strings, file names, and line numbers are stripped at compile time and indexed into a static dictionary (.ldc file). The DSP transmits only compressed 32-bit tokens and parameters, which user-space host tools (sof-logger, dut-monitor, sof_probe_client.py) decode in real time.

  2. Audio Probes & Stream Tap Points: Dynamic non-intrusive tap points attached to pipeline interconnect buffers. Probes allow host developers to extract uncompressed PCM audio at any intermediate stage in the signal processing graph (e.g. pre-EQ, post-AEC) or inject reference audio directly into running pipelines without reconfiguring topologies.

  3. Hardware Telemetry & Performance Monitoring: Real-time CPU cycle accounting, system tick counters, active power state transitions, and component cycle budgets published to shared memory windows (SRAM Window 0 and Window 3). Host drivers and performance monitors read these registers to measure per-core DSP load and detect pipeline underruns.

  4. Abstract Debug Streams & Low-Level Debugging: Structured debug packet framing (DEBUG_STREAM_IDENTIFIER 0x1ED15EED) routed over SRAM Window 2 Debug Slots, mailbox debug memory dumps, and GDB target debug stubs.

Shared SRAM Memory Windows Layout#

SOF partitions DSP shared memory windows into distinct diagnostic and telemetry regions:

+-------------------------------------------------------------------------+
|                       Shared SRAM Mailbox Windows                       |
|                                                                         |
|  +-------------------------------------------------------------------+  |
|  | Window 0: Mailbox & Firmware Status Registers (FSR / LEC / LTR)   |  |
|  |   - Offset 0x00: FW Status (FSR)     - Offset 0x04: Last Error    |  |
|  |   - Offset 0x08: Power Status (FPS)  - Offset 0x0C: Secondary STS |  |
|  |   - Offset 0x10: Pipeline State      - Offset 0x14: Peak Volume   |  |
|  +-------------------------------------------------------------------+  |
|  | Window 1: IPC Mailbox (Host Command / DSP Reply Payloads)         |  |
|  +-------------------------------------------------------------------+  |
|  | Window 2: Debug Window Slot Manager (Magic: 0x1ED15EED)           |  |
|  |   - Slot 0: Reserved / Firmware Ready                             |  |
|  |   - Slot 1: Hardware Telemetry (system_tick_info per core)        |  |
|  |   - Slot 2+: Per-core Debug Stream circular buffers               |  |
|  +-------------------------------------------------------------------+  |
|  | Window 3: Performance Measurement Window (ADSP_PMW)               |  |
|  |   - Memory Window 3: Component cycle budgets & profiling slots    |  |
|  +-------------------------------------------------------------------+  |
+-------------------------------------------------------------------------+

#include <src/include/user/debug_stream_slot.h>

struct debug_stream_text_msg#
#include <src/include/user/debug_stream_text_msg.h>

Formatted text message record within a debug stream.

The record payload is length-delimited by hdr.size_words. The text data in msg[] is ASCII/UTF-8 encoded and padded with trailing NUL bytes to a 32-bit word boundary. Receivers should calculate maximum payload capacity as (hdr.size_words * sizeof(uint32_t) - sizeof(struct debug_stream_record)) and stop parsing at either the capacity limit or the first internal NUL terminator.
