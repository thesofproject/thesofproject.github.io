148 /* indicates that this DP module did not yet reach its first deadline and
149 * no data should be passed yet to next LL module
150 *
151 * why: lets assume DP with 10ms period (a.k.a a deadline). It starts and finishes
152 * Earlier, i.e. in 2ms providing 10ms of data. LL starts consuming data in 1ms chunks and
153 * will drain 10ms buffer in 10ms, expecting a new portion of data on 11th ms
154 * BUT - the DP module deadline is still 10ms, regardless if it had finished earlier
155 * and it is completely fine that processing in next cycle takes full 10ms - as long as it
156 * fits into the deadline.
157 * It may lead to underruns:
158 *
159 * LL1 (1ms) ---> DP (10ms) -->LL2 (1ms)
160 *
161 * ticks 0..9 -> LL1 is producing 1ms data portions, DP is waiting, LL2 is waiting
162 * tick 10 - DP has enough data to run, it starts processing
163 * tick 12 - DP finishes earlier, LL2 starts consuming, LL1 is producing data
164 * ticks 13-19 LL1 is producing data, LL2 is consuming data (both in 1ms chunks)
165 * tick 20 - DP starts processing a new portion of 10ms data, having 10ms to finish
166 * !!!! but LL2 has already consumed 8ms !!!!
167 * tick 22 - LL2 is consuming the last 1ms data chunk
168 * tick 23 - DP is still processing, LL2 has no data to process
169 * !!! UNDERRUN !!!!
170 * tick 19 - DP finishes properly in a deadline time
171 *
172 * Solution: even if DP finishes before its deadline, the data must be held till
173 * deadline time, so LL2 may start processing no earlier than tick 20
174 */
175 bool dp_startup_delay;
